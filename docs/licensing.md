# 授权模型：Open Core

## 一句话

**核心功能 MIT 开源，随便用（含商用）；企业级功能闭源，单独授权。**

本仓库 = 核心。商业模块在独立仓库，不在这里。

## 边界

### 开源核心（本仓库，MIT）

够一个人或小团队把代理跑起来、接进自己的工具链：

| 能力 | 说明 |
|---|---|
| 三种客户端协议 | OpenAI Chat Completions、OpenAI Responses、Anthropic Messages |
| 上游供应商抽象 | rcouyi 面板 + 通用 openai-chat / openai-responses / anthropic |
| 协议转换与事件归一化 | `ChatCore`：提示词注入、推理块分流、工具调用解析 |
| 流式转发 | SSE / 纯文本流，逐块下发 |
| 配置化部署 | `appsettings.json` + 环境变量 |
| Native AOT 单文件发布 | 目标机器无需 .NET 运行时 |
| 结构化日志 | JSONL，每请求带 req id 与上游原文诊断 |

### 商业模块（闭源，需授权）

面向"多人 / 多团队 / 要审计"的组织：

| 能力 | 解决什么问题 |
|---|---|
| 多租户与 API Key 管理 | 一个实例服务多个团队，各自独立 key |
| 配额、限流与成本核算 | 按 key / 模型统计 token 消耗，超限拒绝 |
| 管理后台 | 可视化配置 provider、key、配额、查看用量 |
| 审计日志与合规留存 | 谁在什么时候调了什么模型，可导出、可设保留期 |
| SSO / OIDC / LDAP 集成 | 接入企业现有账号体系 |
| 可观测导出 | Prometheus / OpenTelemetry，接企业监控与告警 |
| 多实例协同 | 共享状态、灰度、熔断、健康检查 |
| 私有 Provider 适配 | 对接企业内部网关或自建推理服务 |

## 为什么这样切

切分依据不是"功能多寡"，而是**谁在为什么付费**：

- 个人开发者要的是"能跑通"，核心功能全给了，不设卡；
- 组织的痛点不是"能不能跑"，而是"跑起来之后管不住"——配额、审计、权限、可观测。这些功能天然要维护成本，也天然有人愿意付钱。

核心 MIT 还有个副作用是好事：**扩散不受限**。任何人不问自取就能用上，用得顺了才会来问企业版。

## 需要诚实面对的一点

MIT 意味着**任何人都能拿核心代码去做自己的商业产品**，包括在上面加自己的企业功能再卖——他们不需要向你付费。

这是 Open Core 的固有代价，靠的不是"防"，而是两个现实：

1. 企业功能要持续维护（对接 SSO、适配各家监控、处理合规），自己造一遍不划算；
2. 出问题时有人负责。买授权本质上是买"有人管"。

如果这点不能接受，那 Open Core 就不合适，该回去考虑非商业协议（如 PolyForm Noncommercial）。

## 贡献

- **核心仓库**接受外部贡献，采用 **DCO**（提交时 `Signed-off-by`），不需要签 CLA。
- **商业模块**独立闭源仓库，不接受外部贡献。
- 核心仓库里**不得混入**商业模块代码，边界必须保持干净——否则整个核心的 MIT 授权会被污染。

## 版权归属

版权由项目所有者持有。如需以公司名义运营、或计划对外提供商业授权，建议尽早把版权归属（个人 vs 实体）理清，并让律师审一份商业授权合同模板。

> 本文是工程视角的取舍说明，不构成法律意见。
